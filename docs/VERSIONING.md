# 版本迭代规范

本文档定义本项目的版本编号、发布门禁与文档同步纪律。所有迭代（无论大小）按此执行，
保证「代码里的版本、分发包的版本、文档里的版本」三处永远一致，任何历史版本可追溯、可复现。

## 1. 版本编号

遵循[语义化版本](https://semver.org/lang/zh-CN/)：`主.次.修订`（如 1.6.0）。

| 位 | 何时递增 | 典型内容 |
|---|---|---|
| 主版本 | 玩家存档不兼容的破坏性变更（存档结构废弃、玩法重置） | 预留 |
| 次版本 | 新功能、新内容（棋子/羁绊/装备/场景）、可见的体验改动、平衡断面移动 | 新场景、64 棋子扩军、典藏音乐 |
| 修订版 | 纯修复（正确性 / 资源生命周期 / 崩溃）、文档与工具链，不改可见行为 | 坐标修复、泄漏清扫 |

判定口诀：**玩家能看见或能玩到差异 → 次版本；只有坏的东西变好了 → 修订版**。
一次迭代同时含功能与修复时，按最高位计（功能 + 修复 = 次版本）。

## 2. 版本三处一致（锁版状态）

版本信息只有两个数据源，加一份日志，三处必须同值：

| 位置 | 字段 | 消费方 |
|---|---|---|
| `src/version.ts` | `GAME_VERSION` / `GAME_BUILD` | 主菜单落款、金种子快照元信息 |
| `package.json` | `version` | 发布脚本（zip 命名、使用说明） |
| `docs/CHANGELOG.md` | 顶部条目 | 人类可读的发布历史 |

`npm run release`（`scripts/release.mjs`）在构建前校验前两者的字面一致，不一致即失败 ——
"zip 是 1.4.0、界面显示 1.4.1" 的错版分发从门禁上杜绝。

## 3. 发布流程（每个版本一条 commit）

```
npm run typecheck        # 1. 类型零错误
npm test                 # 2. 全量回归绿（数量写进 QA.md §1/§3/§11）
npm run release          # 3. 版本校验 + 测试 + 双形态构建 + zip + 产物体检
```

发布纪律：

1. **一条版本一条 commit**，消息以 `feat:/fix:/chore:` 开头并在正文列出要点；
   该 commit 即版本的锚点（tag 可选，commit 本身可追溯）。
2. **金种子快照**：任何影响战斗内核的改动（`core/`、`data/`、涉及 rng 消费顺序的
   `game/` 改动）落地后跑 `UPDATE_GOLDEN=1 npm test` 再生 `battle-golden.json`，
   并在 CHANGELOG 条目中注明漂移的用例与原因。不允许无记录的金种子变更。
3. **平衡断面**：改了 `data/` 数值或超时/裁定口径，必须重跑 `npm run sim` 并把
   新极差/先手写回 QA.md §4 与 README 的平衡态段。
4. **文档同步先于 commit**：CHANGELOG 新条目 + QA/README 中被本次改动影响的所有
   数字（测试数、包体、性能、平衡值）一次改齐，不留"下个版本再补"。

## 4. CHANGELOG 条目规范

- 采用 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 分节：
  新增 / 变更 / 修复 / 移除；顶部条目 = 当前版本。
- 标题行：`## [x.y.z] - 日期 · 一句话主题`。
- 条目写**行为与口径**，不写"修了 XX 问题"的过程叙事（补丁式口吻禁止）：
  每条自含完整语义，读者不需要知道上一次迭代的历史即可理解当前规则。
- 数字（胜率、包体、测试数）随条目落定，作为该版本的存证。

## 5. 文档真源与同步责任

| 变更面 | 必须同步的文档 |
|---|---|
| 版本号 | `src/version.ts` + `package.json` + CHANGELOG 顶部 |
| 测试数量/覆盖 | QA.md §1 / §3 / §11 |
| 数值与平衡 | QA.md §4 + README 平衡态段 +（机制级）DESIGN |
| 视觉/布局规格 | ART_BIBLE（代码镜像：`palette.ts` / `kit.ts`） |
| 操作/打包/产物 | README 对应节 |
| 发布流程变更 | 本文（VERSIONING.md） |

## 6. 遗留约定

- `0.x` 阶段（M2 之前）以里程碑代号（0/F/R/M1）归档于 UPGRADE.md，
  `1.0.0` 起进入语义化版本，历史见 CHANGELOG。
- 未发布的中间状态不占版本号：开发分支上的改动统一并入下一次版本 commit。
- 存档兼容性：`save.ts` 内部带载荷版本（v2→v3 迁移先例）；次版本迭代必须保证
  旧档可读（迁移或回退），主版本才允许弃档。
