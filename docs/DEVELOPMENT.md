# 百战天元 · 开发流程规范

本文是项目开发流程的唯一入口，适用于人工与 AI 协作。目标是用最少的固定步骤持续交付
可解释、可验证、可回退的改动，而不是增加审批和表格。

## 1. 文档职责

| 文档 | 唯一职责 |
|---|---|
| 本文 | 从需求、实现、验证到提交、推送的开发生命周期 |
| [DESIGN.md](./DESIGN.md) | 玩法、架构动机、数值方法与当前设计结论 |
| [QA.md](./QA.md) | 自动门禁、风险矩阵、专项验证和通过标准 |
| [VERSIONING.md](./VERSIONING.md) | 版本号、CHANGELOG、正式发布与回退 |
| [ART_BIBLE.md](./ART_BIBLE.md) | 视觉、动效、字体和 UI 规范 |
| [CHANGELOG.md](./CHANGELOG.md) | 已发布的玩家可见变化与版本历史 |
| [adr/](./adr/) | 少量跨层、长期有效且难以逆转的工程决策 |
| [UPGRADE.md](./UPGRADE.md) | 已完成重构的历史执行记录，不承载现行规则 |

同一规则只写在一个真源中，其他位置使用链接。测试数量、包体、性能和平衡数据只在产生
证据的文档或历史版本中记录，不复制到多个活文档。

## 2. 开发原则

1. **先定义结果**：开始前写清玩家或工程结果、失败表现和验收证据。
2. **风险决定深度**：小改动保持小；触及存档、资源、确定性、发布或跨层边界时加严验证。
3. **最小正确改动**：不顺手重构、不预埋假设性扩展、不为内部实现保留无需求的兼容层。
4. **公开行为优先**：测试稳定领域边界和玩家结果，不把私有字段、布局常量或整对象快照当契约。
5. **真源唯一**：数值、布局、版本和流程规则各有唯一来源，消费方不得复制魔法值。
6. **失败可见**：不重试掩盖、不吞错误、不用降低断言或更新快照解释未知变化。
7. **随时可交付**：每个提交只有一个意图，门禁通过，差异可审查，可以独立回退。

## 3. 标准开发闭环

### 3.1 明确改动

开始前回答三件事：

- 结果：完成后玩家或维护者能观察到什么变化；
- 风险：可能损坏玩法、资产、进度、交互、资源、构建或发布中的哪一项；
- 证据：哪个自动测试、专项模拟或实机步骤能证明结果成立。

无法给出具体失败表现的“顺便优化”不进入本次改动。跨层且长期有效的决策先写 ADR；普通
实现选择直接体现在代码和提交说明中。

### 3.2 建立上下文

```bash
git fetch origin
git status --short --branch
git log --oneline -10
```

先读目标模块、调用方、现有测试和对应规范，不根据文件名猜实现。工作区干净且仅落后远端时，
使用 `git pull --ff-only`；共享工作区有未提交改动时，不执行 pull、rebase、stash、reset 或
checkout，先区分文件归属。无关改动继续保留；同一文件发生直接冲突时停止并协调。

### 3.3 选择改动边界

| 目录 | 职责 | 允许依赖 |
|---|---|---|
| `src/core` | 无头、确定性的战斗内核 | `core`、纯 `data` |
| `src/data` | 棋子、羁绊、装备和调参数据 | `data`、`core` 类型或常量 |
| `src/game` | 对局、经济、AI、卡池、存档和撤销 | `game`、`core`、`data` |
| `src/render` | Phaser 场景、棋盘、特效与输入表现 | `render`、`ui`、`game`、`core`、`data`、`audio`、`music`、`assets`；npm 包 |
| `src/ui` | 可复用界面组件 | `ui`、`render`、`core`、`data`、`audio`、`music`；`game` 仅限 save（偏好）与 state（类型/查表）白名单 |
| `src/audio`、`src/music` | 音频执行与曲目清单 | `audio` → `music`；`music` 自含；不读对局状态 |

`core` 不得读取 DOM、存储、系统时间或全局随机源；`data` 不得依赖运行时场景；`game` 不得
反向引用渲染、UI 或音频。`npm run check:boundaries` 按本表对七层全部文件执行检查
（含 npm 包与白名单规则），名单外引用即失败。新规则优先进入 `data` / `config`，表现层只消费结果。

### 3.4 实现与反馈

1. 先运行最接近风险的现有测试，确认基线。
2. 缺少行为保护时，先写能复现具体故障的最小测试。
3. 实现满足结果的最小改动，保持已有命名、类型和数据流。
4. 立即运行定向测试；失败先定位根因，不同时修改产品与断言猜结果。
5. 删除临时日志、探针、生成物和过期分支，再运行完整门禁。

常用反馈命令：

```bash
npm run test:watch
npm test -- tests/<target>.test.ts
npm run typecheck
npm run qa
```

专项验证按 [QA.md §4](./QA.md#4-变更矩阵) 取并集。Canvas、WebGL、音频上下文和真实指针
行为必须使用 `.qa/smoke-checklist.md` 在前台窗口检查，源码阅读不能代替实机结果。

### 3.5 自审与完成定义

提交前同时满足：

- 改动只解决已定义结果，没有无关重构或生成物；
- 新增复杂度有现实需求，异常路径和状态回滚已处理；
- `npm run qa` 与所有受影响领域的专项门禁通过；
- 文档真源已同步，历史 CHANGELOG 未被改写；
- staged diff 只含本次文件，能够用一句提交标题准确概括；
- 未完成的实机、性能或发布检查被明确记录，不能用“应该没问题”代替。

## 4. 代码判断标准

### 4.1 状态与错误

- 在输入边界拒绝损坏数据，内部逻辑不重复做同一校验；
- 涉及金币、卡池、棋子、装备和存档的操作必须保持原子性，失败后状态与执行前一致；
- 可恢复的浏览器能力失败允许降级，但必须保留确定的回落行为；
- 非法战斗输入、破坏不变量的状态和发布体检失败应立即终止，不能静默修补；
- 兼容代码只服务已发布存档或明确外部消费者，并写明移除条件。

### 4.2 确定性与性能

- 战斗随机只来自注入的 `Rng`，禁止 `Math.random()`；固定步长逻辑不读取墙上时钟；
- 热路径避免每 tick 创建临时集合、纹理或显示对象；静态 Graphics 优先烘焙；
- 优化必须先有可复现基线，再比较同场景结果；没有数据不做复杂缓存；
- 性能改动不能改变随机消费顺序、事件顺序或资源守恒。

### 4.3 可读性

- 命名表达领域含义，函数保持单一目的；只在确有复用或边界价值时抽象；
- 注释解释口径、失败模式和不直观的取舍，不复述代码；
- 不保留注释掉的代码、临时兼容别名、无消费者的配置项或“以后可能用”的扩展点；
- 沿用项目 TypeScript strict、两空格缩进和现有模块风格，不增加纯格式治理工具。

## 5. 依赖与安全

运行时依赖必须少而明确。新增或升级依赖前确认：现有代码不能低成本解决、许可证允许分发、
浏览器包体和初始化成本可接受、维护状态正常。依赖变更必须提交 `package-lock.json`，并执行：

```bash
npm run audit:deps
npm run qa
```

Dependabot 每月合并同类小版本更新；机器人 PR 是主干直提模式的唯一常规例外。重大版本升级单独
处理，不与功能改动混合。

仓库、日志、截图和构建产物不得包含令牌、账号、私钥或玩家隐私数据。外部数据在边界校验；
第三方代码、字体、图片和音乐必须记录来源与许可证。正式发布前，授权清单必须覆盖实际打包的
运行时依赖与媒体资源。

## 6. 主干提交与同步

项目采用主干开发。一个提交对应一个可独立验证的逻辑变化，不按文件类型拆提交，也不把多个
无关修复塞进一次“整理”。

提交前检查：

```bash
git status --short --branch
git diff --check
git diff --cached
git log --oneline -10
```

只显式暂存本次文件。共享工作区中不得使用 `git add .`；不得回退、暂存或提交他人改动。

提交标题使用项目化 Conventional Commits：

| 前缀 | 用途 |
|---|---|
| `feat:` | 玩家可见的新能力或内容 |
| `fix:` | 正确性、崩溃、资源或体验缺陷 |
| `refactor:` | 行为不变的结构改进 |
| `test:` | 测试策略与场景保护 |
| `docs:` | 仅文档变化 |
| `perf:` | 有基准证据的性能改进 |
| `build:` / `ci:` | 构建、发布工具或 CI |
| `chore:` | 无更合适类别的维护工作 |

标题写结果，不写“更新”“调整若干”。正文只在需要解释原因、取舍、迁移或验证证据时添加。

提交后、推送前再次执行 `git fetch origin`。若远端未前进，直接 `git push origin main`；若远端
已前进，不强推。工作区干净时使用 `git pull --ff-only`；存在共享未提交工作时停止同步并协调，
不要用 rebase 或 stash 搬动他人状态。推送后的 CI 是复核，不替代本地门禁。

## 7. 文档与决策

只有规则真源需要同步：玩法和架构写 DESIGN，验证方式写 QA，视觉写 ART_BIBLE，版本和发布写
VERSIONING。README 只保留玩家入口、快速命令和文档导航，不复制会漂移的测试数、包体或完整
平衡断面。

以下情况写 ADR：跨越多个目录、未来修改代价高、存在两个以上合理方案、需要长期保留取舍原因。
ADR 记录背景、决策、替代方案和后果，不记录执行清单。普通修复、局部重构和可轻易撤销的选择
不写 ADR。

CHANGELOG 只记录已发布且玩家可感知的行为、兼容性和分发变化。历史条目是版本证据，不因当前
实现变化而改写；开发过程和测试文件名不进入条目。

## 8. 发布与回退

正式发布遵循 [VERSIONING.md](./VERSIONING.md)。最小顺序为：锁定版本与 CHANGELOG、运行
`npm run qa` 和领域专项、完成实机冒烟、执行 `npm run release`、验证产物后创建版本标签并
推送。发布命令内部再次执行关键门禁，并追加生产依赖与第三方授权审计。

`release/` 是本地生成目录，不是历史归档。每个已分发版本必须把 zip 与授权清单保存到对应的
GitHub Release 或外部版本化存储，并关联同一 `v<版本>` 标签。

出现玩家存档损坏、无法启动、资源丢失或错误发布包时，立即停止继续分发：

1. 记录受影响版本、复现条件和数据风险，不在故障版本上继续叠功能；
2. 重新分发上一标签对应的已验证产物；没有归档时，在干净临时工作区从该标签重建；
3. 用修订版完成根因修复，重跑完整发布链，并在 CHANGELOG 说明兼容与恢复方式；
4. 禁止删除历史或强推覆盖已发布标签。

视觉瑕疵和非阻断性能问题进入下一修订版；启动失败、存档/资产错误、确定性破坏和发布包缺失
属于立即回退或热修复的问题。
